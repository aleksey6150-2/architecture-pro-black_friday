## Архитектурное решение


###  Коллекция orders (заказы)

```json

{
  "_id": ObjectId,
  "user_id": UUID,
  "order_date": ISODate,
  "items": [
    {
      "product_id": ObjectId,
      "price": NumberDecimal,
      "quantity": NumberInt
    }
  ],
  "status": String, // "new", "paid", "shipped", "delivered", "cancelled"
  "total_amount": NumberDecimal,
  "geo_zone": String // "Moscow", "SPB", "Kazan", etc.
}
```

#### Основные операции:

insertOne - быстрое создание заказов

find({user_id: X}) - история заказов пользователя

find({_id: X}) - статус конкретного заказа

### <a name="_3bfxc9a45514"></a>**Кандидаты в шард-ключи:**
|  **Ключ**  | **Плюсы**                                                         | **Минусы**                                                              | **Вердикт**       |
|:----------:|:------------------------------------------------------------------|-------------------------------------------------------------------------|-------------------|
|  user_id   | Отлично для поиска истории пользователя Равномерное распределение | Заказы одного пользователя в одном шарде (может быть проблемой для VIP) | основной кандидат |
|    _id     | Уникальность Хорош для точечных запросов                          | Не покрывает поиск по пользователю                                      | Не подходит       |
|  geo_zone  | Сильная неравномерность (Москва > Калининград)                    | Дисбаланс шардов                                                        | Плохой выбор      |
| order_date | Все новые заказы в один шард                                      | Горячая точка записи                                                    | Не подходит       |


#### Рекомендация:
Использовать user_id как шард-ключ с хэшированным индексированием (hashed).

#### Обоснование:
* Запросы истории заказов (find({user_id: X})) будут направляться в один шард — быстро и эффективно
* Хэш обеспечивает равномерное распределение пользователей
* Все заказы одного пользователя хранятся вместе — удобно для транзакций
* Заказы распределяются по шардам случайно, нет "горячих" шардов

###  Коллекция products (товары)

```json
{
  "_id": ObjectId,
  "name": String,
  "category": String, // "electronics", "books", "audio", "home_appliances"
  "price": NumberDecimal,
  "stock_by_zone": {
    "Moscow": NumberInt,
    "SPB": NumberInt,
    "Kazan": NumberInt,
    // ... другие геозоны
  },
  "attributes": {
    "color": String,
    "size": String,
    // ... другие атрибуты
  }
}
```
Основные операции:
* Частые обновления stock_by_zone при покупках
* Поиск по категориям и фильтрация по цене
* Точечное чтение товара по _id

Кандидаты в шард-ключи:
### <a name="_3bfxc9a45514"></a>**Кандидаты в шард-ключи:**
|    **Ключ**    | **Плюсы**                                            | **Минусы**                                        | **Вердикт**       |
|:--------------:|:-----------------------------------------------------|---------------------------------------------------|-------------------|
|    category    | Хорош для поиска по категориям                       | Неравномерное распределение (electronics > books) | Не подходит       |
|      _id       | Равномерное распределение Быстрый точечный доступ    | Не помогает при поиске по категориям              | Неоптимально      |
| category + _id | Компромисс: группировка по категориям + уникальность | Сложнее в управлении                              | Основной кандидат |
|     price      | Сильная неравномерность                              | Хот-споты                                         | Не подходит       |

#### Рекомендация:
Использовать составной шард-ключ { category: 1, _id: 1 } с диапазонным шардированием (ranged) на категории и уникальностью через _id.

#### Обоснование:
Поиск по категориям (find({category: "electronics"})) будет направлен в один или несколько шардов
Добавление _id гарантирует уникальность и предотвращает проблемы с "jumbo chunks"
Товары одной категории хранятся компактно — эффективное использование индексов
Обновления остатков распределяются по категориям, нет единой точки записи

###  Коллекция carts (корзины)
```json
{
  "_id": ObjectId,
  "user_id": UUID,          // для авторизованных
  "session_id": String,      // для гостей
  "items": [
    {
      "product_id": ObjectId,
      "quantity": NumberInt
    }
  ],
  "status": String, // "active", "ordered", "abandoned"
  "created_at": ISODate,
  "updated_at": ISODate,
  "expires_at": ISODate // TTL индекс
}
```
Основные операции:

* Поиск активной корзины: { session_id: X, status: "active" } или { user_id: X, status: "active" }
* Добавление/удаление товаров
* Слияние корзин при логине
* Автоматическое удаление старых корзин (TTL)

### <a name="_3bfxc9a45514"></a>**Кандидаты в шард-ключи:**
|  **Ключ**  | **Плюсы**                                  | **Минусы**                               | **Вердикт** |
|:----------:|:-------------------------------------------|------------------------------------------|-------------|
|  user_id   | Равномерно                                 | Не покрывает гостевые сессии             | Не подходит |
| session_id | Покрывает гостей                           | Не покрывает авторизованных              | Не подходит |
|    _id     | Уникальность                               | е покрывает поиск по сессии/пользователю | Не подходит |
|   status   | Сильная неравномерность (active < ordered) | Дисбаланс                                | Не подходит |

Проблема: Нам нужно быстро искать корзину по двум разным полям (session_id или user_id). Создать custom key - пользовательский ключ owner_id, который объединяет оба идентификатора

Стратегия: Использовать owner_id как хэшированный шард-ключ.
