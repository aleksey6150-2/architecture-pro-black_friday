# Анализ стратегий чтения с реплик для коллекций MongoDB

## 2. Анализ коллекции `products` (Товары)

### Характеристики:
- **Частота обновлений**: Очень высокая (остатки меняются при каждой покупке)
- **Критичность консистентности**: Критическая для остатков, низкая для описаний
- **Типичные операции**:
    - Поиск товаров по категориям (фильтрация, пагинация)
    - Просмотр карточки товара
    - Проверка остатков при добавлении в корзину
    - Обновление остатков при покупке

### Операции чтения и стратегия:

| Операция | Тип чтения | Стратегия | Обоснование |
|----------|------------|-----------|-------------|
| **Поиск товаров по категориям** | Множественное чтение | **SECONDARY** (preferred) | Небольшая задержка допустима, снижаем нагрузку на primary |
| **Просмотр карточки товара** | Точечное чтение | **SECONDARY** (preferred) | Описание товара меняется редко, задержка не критична |
| **Проверка остатков перед добавлением в корзину** | Точечное чтение | **PRIMARY** | Критично: если прочитать устаревший остаток с secondary, можно продать товара больше, чем есть в наличии |
| **Проверка остатков при оформлении заказа** | Точечное чтение | **PRIMARY** | Аналогично: финальная проверка должна быть по актуальным данным |
| **Админ-панель управления товарами** | Все операции | **PRIMARY** | Администраторы должны видеть точную картину |

**Допустимая задержка репликации:**
- Для поиска и карточек товаров: **до 30 секунд** (пользователи простят небольшую задержку в выдаче)
- Для проверки остатков: **0 секунд** (только primary)

## 3. Анализ коллекции `orders` (Заказы)

### Характеристики:
- **Частота обновлений**: Средняя (создание заказов + смена статусов)
- **Критичность консистентности**: Высокая для статусов, средняя для истории
- **Типичные операции**:
    - Создание заказа (запись)
    - Просмотр истории заказов пользователя
    - Проверка статуса конкретного заказа
    - Обновление статуса заказа

### Операции чтения и стратегия:

| Операция | Тип чтения | Стратегия | Обоснование |
|----------|------------|-----------|-------------|
| **Просмотр истории заказов пользователя** | Множественное чтение | **SECONDARY** (preferred) | Пользователь редко проверяет историю сразу после заказа, задержка допустима |
| **Проверка статуса заказа** | Точечное чтение | **PRIMARY** или **SECONDARY с maxStaleness** | Если заказ только что обновлен (оплачен, отправлен), пользователь ожидает увидеть актуальный статус. Допустимо чтение с secondary с ограничением staleness ≤ 10 секунд |
| **Проверка статуса "свежего" заказа (до 5 минут)** | Точечное чтение | **PRIMARY** | Сразу после оформления пользователь несколько раз проверяет статус — нужна максимальная актуальность |
| **Просмотр заказов менеджером** | Все операции | **PRIMARY** | Операционные задачи требуют точных данных |
| **Аналитические отчеты по заказам** | Множественное чтение | **SECONDARY** | Отчеты могут строиться на slightly stale данных |

**Допустимая задержка репликации:**
- Для истории заказов: **до 1 минуты**
- Для статусов заказов старше 5 минут: **до 10 секунд** (с контролем `maxStaleness`)
- Для статусов "свежих" заказов: **0 секунд**

## 4. Анализ коллекции `carts` (Корзины)

### Характеристики:
- **Частота обновлений**: Очень высокая (постоянные изменения при добавлении/удалении товаров)
- **Критичность консистентности**: Максимальная для активной корзины
- **Типичные операции**:
    - Чтение текущей корзины (гость/пользователь)
    - Добавление товара в корзину
    - Удаление товара из корзины
    - Слияние корзин при логине
    - Отметка корзины как заказанной

### Операции чтения и стратегия:

| Операция | Тип чтения | Стратегия | Обоснование |
|----------|------------|-----------|-------------|
| **Получение текущей корзины (активная сессия)** | Точечное чтение | **PRIMARY** (strongly consistent) | Пользователь должен видеть точное содержимое корзины. Если прочитать stale данные, он может подумать, что товар пропал или не добавился |
| **Проверка корзины перед оформлением заказа** | Точечное чтение | **PRIMARY** | Финальная проверка должна быть по актуальным данным |
| **Админ-просмотр брошенных корзин** | Множественное чтение | **SECONDARY** | Для анализа брошенных корзин допустима задержка |
| **Восстановление корзины после сбоя** | Точечное чтение | **PRIMARY** | Критично для пользовательского опыта |

**Допустимая задержка репликации:**
- Для активной корзины пользователя: **0 секунд** (только primary)
- Для аналитических запросов: **до 1 минуты**

## 5. Обоснование выбора стратегий

### 5.1. Почему `products` может читать с secondary для поиска?

**Бизнес-логика:** Пользователь ищет товары по каталогу. Если товар только что добавили или изменили цену, но на secondary эти изменения еще не попали, пользователь:
- Либо не увидит новый товар в выдаче (но он может повторить поиск позже)
- Либо увидит старую цену (но при переходе в карточку или добавлении в корзину проверится актуальная)

**Риск:** Минимальный. Продажи не пострадают, пользовательский опыт немного ухудшится.

### 5.2. Почему `products` требует primary для проверки остатков?

**Бизнес-логика:** Проверка остатков происходит в момент добавления в корзину и оформления заказа. Если прочитать stale данные с secondary, можно:
- Разрешить добавить в корзину товар, которого уже нет в наличии
- Подтвердить заказ с товаром, который закончился

**Риск:** Критический. Продажа отсутствующего товара → негативный опыт, возвраты, репутационные потери.

### 5.3. Почему `orders` может использовать secondary с ограничением staleness?

**Бизнес-логика:** После оформления заказа пользователь обычно проверяет статус несколько раз в первые минуты. Если задержка репликации больше 10 секунд, он может:
- Не увидеть подтверждение оплаты
- Не увидеть изменение статуса на "отправлен"

**Риск:** Средний. Пользователь может начать звонить в поддержку, создавая лишнюю нагрузку. Но бизнес-процесс не нарушается.

### 5.4. Почему `carts` требует только primary?

**Бизнес-логика:** Корзина — это состояние сессии пользователя. Она постоянно меняется. Если прочитать stale данные:
- Пользователь не увидит только что добавленный товар
- Пользователь увидит уже удаленный товар
- При слиянии корзин могут возникнуть конфликты

**Риск:** Высокий. Пользователь подумает, что сайт "глючит", и может уйти к конкурентам.

## 6. Заключение

Предложенная стратегия балансирует между:
- **Производительностью** (снижение нагрузки на primary на 60-70%)
- **Консистентностью** (критические операции всегда на primary)
- **Бизнес-рисками** (продажа несуществующего товара исключена)

Ключевые принципы:
1. **Критичные данные** (остатки, активная корзина) — только primary
2. **Некритичные данные** (поиск, история) — secondary
3. **Промежуточные данные** (статусы заказов) — secondary с контролем staleness
